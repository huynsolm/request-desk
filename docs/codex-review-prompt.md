````text
너는 독립 코드 검수자야. 구현자(Claude)가 만든 "리퀘스트 데스크" 1단계 변경을 검수해줘.

## 대상
- 저장소 루트: request-desk (1단계 구현 커밋 6abfaa4 이후의 HEAD. 아래 "0. 검수 대상 확인" 참조)
- 앱 목적: 담당자 1명이 고객 요청을 입력 → 원문과 분석 비교 → 수정·검토 → 요구사항 확정 → 작업 생성 → 상태 관리. 로컬 개발용(로그인 없음).
- 스택: Node 24 + Hono + node:sqlite(SQLite) / React + Vite + TypeScript / Vitest / Playwright

## 0. 검수 대상 확인 (가장 먼저, 코드 변경 없이)
```bash
git rev-parse HEAD
git status --short
git log --oneline 6abfaa4^..HEAD
```
- 현재 HEAD 가 무엇인지, 미커밋 변경이 있는지 확인하고, **실제로 검수한 커밋 해시를 보고서 맨 위에 적어줘.**
- 구현 기준 커밋은 6abfaa4 이고, 그 뒤에 보안 보강 커밋이 있을 수 있다. 6abfaa4 이후 변경도 검수 범위에 포함해줘.
- 미커밋 변경이 있으면 검수 대상에 포함하지 말고(또는 따로 표시하고) 알려줘.

## 안전 규칙 (실행 전에 꼭 지켜줘)
- **개발 DB(`data/app.db`)를 초기화하거나 지우지 마.** `npm run db:reset` 은 파일을 삭제하고 다시 만든다. 기본 경로로 실행하지 말고, 반드시 별도 경로를 지정해서만 실행해줘.
  - PowerShell: `$env:DB_PATH='data/review.db'; npm run db:reset -- --morning-analysis`
  - bash: `DB_PATH=data/review.db npm run db:reset -- --morning-analysis`
  - 서버도 같은 `DB_PATH` 로 띄운다. 검수가 끝나면 `data/review.db*` 만 지워도 된다(`data/app.db` 는 건드리지 않는다).
- E2E(`npm run test:e2e`)는 자체적으로 `data/e2e.db` 를 새로 만들어 쓰므로 개발 DB 와 섞이지 않는다.
- 소스 코드, 설정, git 기록을 수정·커밋·push 하지 마. 검수 중 생긴 산출물(`data/review.db*`, `test-results/`, `dist/`)은 git 에 올라가지 않는 파일이다.

## 검수 기준이 되는 핵심 규칙 (원 요구사항)
분석 내용은 세 종류로 구분: ① 명시된 요구사항(고객이 원문에서 직접 말한 것, 원문에 없는 기능·구현 방식 금지) ② 확인할 질문(질문·이유·고객 답변·해결 상태) ③ 미확정 사항(근거 없이 확정 사실·작업으로 바꾸지 않음).
- "검토했는가"와 "내용이 결정되었는가"는 별도 상태. 질문을 읽었다고 답변 완료 처리 금지, 미확정 사항을 검토했다고 확정 요구사항으로 바꾸기 금지.
- 고객 답변을 요구사항으로 반영하려면 사람이 명시적으로 전환하고 근거를 남김.
- 근거 없는 신뢰도 백분율 표시 금지.
- 확정: 활성 항목을 모두 검토해야 가능, 명시된 요구사항 1개 이상, 미해결 질문·미확정은 남길 수 있으나 작업 대상 제외, 확정 시 포함/제외 개수 표시, 확인창에서 사람이 최종 승인, 확정 기록은 당시 내용의 버전으로 보존.
- 수정 규칙: 항목을 수정하면 다시 검토 필요, 확정 후 원문·분석을 바꾸면 새 검토 버전, 기존 확정 기록과 작업은 자동으로 덮어쓰지 않음, 연결된 작업에 원본 변경 사실 표시.
- 작업 생성: 확정된 버전의 명시된 요구사항만, 질문·미확정은 선택 대상 아님, 완료 조건은 확인 가능한 문장(“요청대로 동작한다” 같은 모호한 기본값 금지), 같은 확정 요구사항에서 반복 클릭·재시도로 중복 생성되지 않게 서버와 DB에서도 방지, 확정 요구사항 하나당 작업 하나, 연결 유지.
- 규칙은 화면에서 버튼을 숨기는 것만으로 구현하면 안 됨(서버 검증 필수).
- 첫 버전 제외: 로그인/다중 사용자, 채팅, 결제, 견적, 음성·사진, 외부 서비스 연동, 자동 코드 생성, 통계 대시보드. 실시간 조회·결제·승인/반려·CSV 같은 기능을 원문에 명시된 사실로 샘플에 넣으면 안 됨.

## 집중 검수 항목 (구현자가 위험하다고 본 곳)
1. server/service.ts confirmPreview / confirmRequest — 확정 조건, contentSeq 승인 토큰, 확정 스냅숏. 우회 경로나 경쟁 조건이 있는가?
2. server/db/migrations/0001_init.sql 트리거·CHECK·UNIQUE — 확정 중 잠금, 수정 시 재검토, 인용 검증, 확정 기록 불변, 작업 대상 제한. 서버 로직과 어긋나는 곳이 있는가? 트리거가 막지 못하는 쓰기 경로는?
3. createTasks — 원자성(하나라도 실패하면 아무것도 안 만들어지는가), 멱등성, tasks.source_item_id UNIQUE 와 "다시 검토 → 재확정"의 상호작용(고친 요구사항이 새 작업을 못 만드는 것이 의도에 맞는가)
4. updateRequest / reopenRequest / taskChange() — 새 검토 버전 전환, "원본 변경됨" 계산(저장하지 않고 매번 계산)이 요구사항("연결된 작업에는 원본 변경 사실 표시")을 충족하는가
5. web/src/pages/RequestDetailPage.tsx commitForm, useSaver.ts — 저장 실패·재시도 시 입력값 보존, 대기열 key 중복, 오래된 version 으로 재시도할 때의 동작, 낙관적 업데이트를 쓰지 않은 것이 "저장 실패 시 입력값 보존" 요구에 충분한가
6. 원문 인용 검증이 쓰기 시점에만 DB 에서 검사되고 이후 원문 변경은 quoteValid 로 계산해 확정을 막는 구조가 충분한가
7. shared/validation.ts 의미 없는 입력 기준(글자 수 기반, "2" 같은 입력 거부)이 한국어 입력에 과하거나 느슨한가, 모호한 완료 조건 문자열 규칙의 허점
8. 요구사항 vs 구현 불일치: docs/requirements.md 의 각 행이 실제 코드·테스트로 뒷받침되는가(테스트가 규칙을 진짜로 잡는지, 이름만 있고 vacuous 한 테스트는 없는지)
9. 보안·데이터 안전: 서버가 127.0.0.1 에만 바인딩되는지, SQL 인젝션/LIKE 와일드카드 처리, 입력 크기 제한 부재, 비밀키·DB 파일이 커밋에 없는지
10. **무인증 로컬 서버의 접근 검사**: 127.0.0.1 바인딩만으로는 부족하다. 사용자가 다른 웹사이트를 열어 둔 상태에서 그 사이트가 이 API 로 변경 요청(POST/PATCH/DELETE)을 보낼 수 있는지 확인해줘.
    - server/app.ts 의 `/api/*` 미들웨어: Origin 허용 목록, Host 검사(DNS 리바인딩), Sec-Fetch-Site, Content-Type(JSON 만 허용) 검사가 빠진 경로나 우회 방법이 없는가? 허용 목록에 없는 로컬 포트의 다른 앱, `text/plain`·폼 전송, Origin 이 없는 요청은 어떻게 처리되는가?
    - CORS 응답 헤더를 따로 열어 두지 않았는데(preflight 불필요한 "단순 요청" 포함) 실제로 막히는지 `curl`/테스트로 확인해줘. 검사 자체가 정상 사용(개발 웹, 프로덕션 단일 서버 `npm start`)을 막지는 않는가?
    - tests/server/security.test.ts 가 이를 실제로 잡는지(규칙을 일부러 깨 보았을 때 실패하는지) 판단해줘.
````
